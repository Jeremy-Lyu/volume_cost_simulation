## 1. 逐条说明

### 规则 1：缓存上限 = 车间总量
- 改动：每车间每月 `Σ_m inv[a,m,t] ≤ buffer_cap(a)`（原来按每车型各一份）。
- 影响：基准 +2 万（42,953 → 42,955，patched 已体现）；原版在测试中上限 100 实际存了 300。
- 自检：`selfcheck` 检查"缓存超限"。

### 规则 2：缺口可延期，期末未交付算流失
- 公式：`上月积压 + 本月需求 = 本月交付 + 本月积压`（每车型×月，`bl_{m}_{t}`）；最后一个月的积压 = 流失 `short`，其余月份流失 = 0。
- 成本：`延期成本 = backlog_cost_per_unit_month × Σ(非期末月积压)`；`缺口惩罚(流失) = shortage_penalty × 期末积压`。
- 有成品库时：原"不超配额交付"约束被积压平衡取代（交付不会超过累计需求）。
- 报表新增：`延期台月`、`流失台`；`stress_test` 的"积压月份"改看 bl。
- 参数：`backlog_cost_per_unit_month = 1,500 元/台·月` ⚠ 示例。
- ⚠ 观察：延期成本 1,500 元/台·月低于"加班/开班"的边际成本时，模型会**主动延期**——基准里每年约 900 台·月是"故意推迟到下月"。如果业务上不希望常态延期，应调高延期成本，或加"单月最大积压台数/最长延期 1 个月"约束（v4.1 可加）。

### 规则 3：允许 0 班（整月停线）
- 新增方案 `shifts=0`（只挂在最低 JPH 档，避免重复解）：工时 0、产能 0、人工/班车/外包/变动能耗 0，只计 `停线固定 = idle_fixed_month`。
- 参数：`shop_params.csv:idle_fixed_month = 30 万/车间·月` ⚠ 示例（基础能耗、待岗工资等）。
- 测试：零需求时四个车间全部选 0 班，只付停线固定（原版会付一整班）。
- 本次示例数据各场景都没有选 0 班（需求不够低），只在极端测试中出现。
- ⚠ `head_change` 人数变化约束以上月人数为基数，从 0 班恢复时会受限；若同时使用需另行处理。

### 规则 4：加班上限 36h/人 可突破，班次越多线体加班能力越大
- 变量：`ot`（36h/人 以内）+ `otx`（超出部分）。
- 约束：`ot ≤ 36 × 班次数`、`otx ≤ (绝对上限 − 36) × 班次数`（每个班组都能加班，人均 = 线体加班小时 / 班次数）。
- 成本：加班费按 (ot+otx) 计；超限部分再加 `超限加班溢价 = 班组人数 × ot_excess_premium_per_head_hour × otx`。
- 报表：plan 新增 `ot_excess_hours`（超限加班小时）、`ot_per_head`（人均加班）；汇总新增 `超限加班h`、科目 `超限加班溢价`。
- 参数：`ot_hard_cap_per_head_month = 60h` ⚠、`ot_excess_premium_per_head_hour = 30 元` ⚠。
- 场景/策略里的"加班上限"旋钮（如 稳定优先 24h、练习1 60h）统一用 `dl.set_ot_cap()`，同时设为常规和绝对上限（即严格上限）。
- 加班的人数改为"直接+间接"班组（全成本口径下间接人员也随线加班 ⚠）。

### 规则 5：加班单价 = 小时工资 × 倍数
- `ot_rate = wage_per_head_month / std_hours_month × ot_multiplier` = 9,000/174×1.5 ≈ **77.6 元/时**（原固定 75）。
- 删除 `ot_rate_per_head_hour` 参数；`plant_check` 必填项改为 `std_hours_month、ot_multiplier`。
- 参数：`std_hours_month = 174`（21.75 天×8h）⚠、`ot_multiplier = 1.5`（工作日；休息日 2、法定 3，⚠ 月度模型暂用单一倍数，后续可按加班日类型拆分）。
- 影响：工资+5% 场景加班费同步 +5%（测试通过）。

### 规则 6：两班倒也有夜班补贴
- `夜班补贴 = (直接+间接每班定员) × 每天夜班个数 × 开工天数 × night_allowance_per_head_night`
- `shift_options.csv` 新增 `night_shifts`：1 班=0、2 班=1、3 班=1 ⚠；`global:night_allowance_per_head_night = 30 元/人/夜班` ⚠。
- 原 `night_allowance_per_head`（800 元/人/月，只在 3 班计）列保留但不再使用。
- 例（示例数据，总装 10 月 36×2）：425 × 1 × 18 × 30 = 22.95 万/月。
- 影响：这是 v4 基准成本上升的主要原因之一（两班是最常见的方案）。

### 规则 7：间接人工归入"人工"
- `fixed_breakdown`："人工" = 直接 + 间接 + 夜班补贴，不再单列"间接人工"科目；`account_map` 同步。
- OH 不重复：OH 只含 `oh_fixed_month`（常数）+ `oh_var_per_unit × 产量`，不含任何人工项；`selfcheck` 保证科目合计 = 目标。⚠ 业务侧需确认 `oh_fixed_month` 本身的口径里没有间接人员工资。

### 目标与报表共用一套科目表达式（重构）
- `model_builder.build()` 用 `add(科目, 表达式)` 构造 `acc`，目标 = Σacc；`report.extract()` 直接 `value(acc[科目])`。之前 4 个 P0 都是"目标一套公式、报表另一套"造成的，现在从结构上消除。
- 物料只做口径（`NON_OBJ`），不进目标；边际贡献作为科目 `−边际贡献` 进目标。
- `report.kpis()` 统一口径：运营成本 = 目标 − 流失惩罚 + 边际贡献；单车成本 = 运营成本 / 产量。

### 守恒自检 + golden 基线
- `report.selfcheck()`：科目合计=目标、每车间每月只选一个方案、流平衡、缓存总量≤上限、交付+流失=需求。`run.py / strategies.py / stress_test.py` 每次求解后自动检查，不过即报错。
- `golden.py`：首次运行写 `golden.csv`（v4 基准与 4 场景的总成本、产量、缺口、延期台月），之后每次 `run.py` 自动比对（容差 0.05% 或 2 万元）；改了参数确需更新时 `python3 golden.py --update`。

## 2. 结果对比（原版 / patched / v4，示例数据）

完整表：`对比表_原版_patched_v4.csv`、`对比表.md`。摘要：

| 项目 | 原版 | patched | v4 |
|:--|--:|--:|--:|
| 基准 总成本（万元） | 42,953 | 42,955 | **43,433** |
| 基准 单车成本（元） | 3,579 | 3,580 | 3,619 |
| 基准 加班小时 / 超限加班 | 647 / – | 649 / – | 805 / 59 |
| 基准 延期台月 / 流失 | – / 0 | – / 0 | 900 / 0 |
| 基准 平均缓存（台） | 313 | 313 | 268 |
| 需求+10% | 46,002 | 46,047 | 46,366 |
| 工资+5%（较基准） | +812 | +811 | **+845**（加班单价联动） |
| 稳定优先 | 45,484 | 45,749 | 45,361 |
| 保人力 | 44,033 | 44,154 | 43,636 |
| 需求+20% 低惩罚：流失台 | 11,868 | 11,658 | **1,320**（延期 480 台·月） |
| 蒙特卡洛 成本优先：有缺口样本 | 90% | 90% | **0%**（平均延期 562 台·月） |
| 压力-缺芯：流失台 | 2,030 | 2,030 | **0**（延期 3,783 台·月） |
| 压力-组合冲击：流失台 | 2,508 | 2,505 | 1,879 |
| 全成本口径 目标（万元） | −211,964 | −242,796 | −241,214 |
| 全成本 成品库存（台·月） | 19,271 | 4,394 | 3,385 |

解读：
1. **基准 +480 万（约 +1.1%）** 主要来自两班夜班补贴（规则 6）和加班单价 75→77.6（规则 5）；缓存总量约束和延期机制略有抵消。
2. **缺口的含义变了**：原版"缺口=丢单"，v4 大部分缺口变成"晚一个月交付"，所以流失大幅减少，"成本优先"在随机需求下也不再出现丢单。管理层看结果时要同时看"延期台月"。
3. **稳定优先、保人力 v4 反而便宜**：因为可以用延期和超限加班吸收波动，不必为峰值提前开班或囤缓存。
4. 各场景都没有选 0 班；超限加班在基准中只有 59 小时（总装 10 月等峰值月）。
