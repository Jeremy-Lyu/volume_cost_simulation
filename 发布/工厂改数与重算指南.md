# 工厂改数与重算指南

> 当前可运行代码在 `v5.2/`。`archive/prototype/`、`archive/v4/` 只留作对照，不要在里面改数、也不要拿那里的结果当现口径。
> 本文所有数字都是示例，标 ⚠ 的还没经工厂确认。改完重算出来的仍是示例口径，直到表里换成工厂自己的数，并在 `plant.json` 里改掉配置版本。

工厂要动的事情只有三类。先对上类，再改文件，再按文末的命令重算。

| 想做的事 | 改哪里 | 要不要改 Python |
| :-- | :-- | :-- |
| 基数：工资、需求、定员、日历、电价、库容 | `v5.2/data/` 里对应的 CSV 或 JSON | 不用 |
| 策略：多付多少换稳定、禁三班、加班上限、看哪一种冲击 | 场景库旋钮，或 `strategies.py` 里三种现成策略的约束 | 旋钮不用；三种策略的定义要改代码 |
| 计算：产能怎么乘、加班单价怎么派生、科目怎么进目标 | `cost_functions.py`、`model_builder.py`、`energy.py`、`daily.py` | 要，并且要补测试 |

下面的命令都在 `v5.2/` 目录里执行。需要 PuLP 2.9（`pulp==2.9.0`）。4.x 的接口和这套代码对不上。

## 1. 改之前先做的四件事

1. **留一份本厂配置包，不要直接改示例包后再无法对照。** 把 `v5.2/data/` 整目录复制成 `v5.2/plants/本厂代号/`。以后只改这一份。`plant.json` 里改 `plant_id`、`plant_name`、`config_version`（建议带日期，例如 `TZ-cfg-2026.10-工厂`）、`owner`。
2. **不要运行 `python3 gen_data.py`。** 它会覆盖需求、日历、产能上限、JPH 档、班次、车间参数和全局参数，而且写出的列是更早的口径（没有 0 班、没有 `night_shifts`、加班单价仍写成固定值）。工厂已经填过的数会被盖掉。
3. **每一处 ⚠ 改完，同步改 `data/假设登记表.md`。** 写上新取值、谁确认的、日期。登记表不进求解，漏记以后无法解释结果为什么变了。
4. **改完先检查，再求解。**

```bash
cd v5.2
python3 plant_check.py                 # 检查 data/，示例配置包
python3 plant_check.py plants/本厂代号  # 检查复制出来的配置包
```

结构或规则失败（FAIL）时先补表，不要求解。缺可选表是 WARN，表示这项扩展没启用，基础口径仍能算。

## 2. 基数：改哪张表

必填表缺一列或少一个月，`data_loader.validate` 会直接报错。可选表整文件不存在就等于这项不算。

### 2.1 必填

| 谁维护 | 文件 | 改什么 | 改完模型会怎样 |
| :-- | :-- | :-- | :-- |
| 计划 | `demand.csv` | `month, model, demand`（台） | 产量目标和单车分摊一起变。只改总量时，固定制造费用被摊薄或摊厚，这是分摊，要和「少开班省下的人工」分开看 |
| 计划 | `calendar.csv` | `month, workdays` | 开工日变少，同样 JPH 的月产能下降，停工日天数上升 |
| 计划 / IE | `capacity_limit.csv` | `shop, model, month, cap` | 某车型某月在该车间的产量上限。和「开动率乘在 JPH 上」是两件事 |
| IE | `jph_options.csv` | `shop, jph, heads_per_shift, run_kw` | 模型只能在这些档里选一档。定员必须随 JPH 升高而不下降，否则校验失败 |
| IE / 生产 | `shift_options.csv` | 班次 0/1/2/3 的有效小时、夜班个数 `night_shifts`、班车、外包 | 0 班表示整月停线。两班、三班各有几个夜班看 `night_shifts`，金额看全局参数里的 `night_allowance_per_head_night` |
| 财务 / 生产 | `shop_params.csv` | 单车电耗、OH 固定与单车、加班常规上限、缓存上限与持有、停线月固定 `idle_fixed_month` | 车间加班常规上限不能大于全局绝对上限 |
| 财务 / HR / 能源 | `global_params.csv` | 见下表 | 全厂单价和求解时限 |
| 工厂负责人 | `plant.json` | 工厂代号、车间链顺序、配置版本 | 车间链最后一个车间承接需求。改顺序等于改物流方向，要和业务一起确认 |

`global_params.csv` 里工厂会改的键：

| 键 | 示例值 | 含义 |
| :-- | --: | :-- |
| `wage_per_head_month` | 9000 | 月薪。加班单价由此派生，见第 4 节 |
| `std_hours_month` | 174 ⚠ | 标准月工时 |
| `ot_multiplier` | 1.5 ⚠ | 加班倍数。法定节日 3 倍、休息日 2 倍目前没有按日期拆开，全月用这一个倍数 |
| `ot_hard_cap_per_head_month` | 60 ⚠ | 每人每月加班绝对上限（小时） |
| `ot_excess_premium_per_head_hour` | 30 ⚠ | 超过车间常规上限之后，每小时每人的额外溢价 |
| `night_allowance_per_head_night` | 30 ⚠ | 每个夜班、每个人的补贴。`shift_options.csv` 里的 `night_allowance_per_head` 不参与这笔计算 |
| `elec_price` | 0.75 | 启用分时电价时，作为缩放基准；分时表见第 2.3 节 |
| `shortage_penalty` | 30000 | 期末流失一台的惩罚（元）。有 `margin.csv` 时，目标改为成本减边际贡献，这项不再单独决定「肯不肯丢单」 |
| `backlog_cost_per_unit_month` | 1500 ⚠ | 延期到下月，每台每月的成本 |
| `burden_rate` | 缺省 1.0；全成本示例常用 1.35 ⚠ | 工资上的福利社保系数。1.35 表示再计提 35% |
| `solver_time_limit` | 120 | 单次求解秒数。调小会停在尚未证最优的可行解上，总成本可以和上次差几十到一两百万，仍打印 Optimal |
| `mip_rel_gap` | 0.0001 | 相对间隙。间隙放宽，求解变快，和 golden 的差会变大 |

如果表里还有 `ot_rate_per_head_hour`，读入时会被丢掉。加班单价只由月薪、标准月工时和倍数算出。

### 2.2 人工弹性和换档（有文件才启用）

| 文件 | 列 | 示例 ⚠ | 注意 |
| :-- | :-- | :-- | :-- |
| `labor_flex.csv` | `dispatch_share` | 0.20 | 只能当成「派遣 + 临时工」合计。法规派遣上限是用工总量的 10%，口径要 HR 确认 |
| 同上 | `stopday_pay_regular` / `stopday_pay_dispatch` | 0.70 / 0 | 停工日正式工发七成、派遣不发。可省比例 φ = (1−派遣比)×(1−正式工发薪) + 派遣比×(1−派遣发薪)。示例 φ = 0.44 |
| 同上 | `borrow_limit` | 0.10 | 月度模型按人·天凑平，同一天有没有空人它不管。按天核对焊装和涂装同日开工时，借调可以是 0。月度结果里的借调净额不要当成已落实的节约 |
| 同上 | `paid_days_month` | 21.75 | 月薪折到日薪的天数 |
| `jph_switch.csv` | `cost_per_switch`, `lost_days` | 300000, 2 | 相邻月换一档的费用，以及少掉的产出天数 |

删掉这两个文件，等于关闭停工日节省、借调和换档成本，口径回到没有这两项的算法。

### 2.3 能源（有这些文件就走分时）

| 文件 | 改什么 |
| :-- | :-- |
| `energy_config.json` | `tou_version`（`2026` 或 `2024`）、`voltage`、`purchase_mode`、`market_price_factor`、`demand_charge_kw_month` 需量电价、`demand_coincidence`、`gas_price`、`heatup_window_end` |
| `tou_price.csv` / `tou_periods.csv` | 分时电价和时段 |
| `shift_times.csv` | 早、中、夜、加班的起止时刻。电价按时段加权，时刻改了，班次电价就变 |
| `shop_energy.csv` | 待机比例、天然气、启炉能耗、电泳保温、周末/夜间 `hold` 或 `shutdown` 或 `auto` |

`energy_config.json` 里 `tou_enabled` 设为 false，月度能源回到「运行功率 × 小时 × `elec_price`」这一档，分项（待机、气、启停、需量）不再单列。

### 2.4 按天排产（焊装 → 白车身缓存 → 涂装）

只改 `daily_config.json`：月份、当月需求台数、库容上下限和初值、车身价值、资金率、休息日加班倍数、是否允许周末开工、`allow_borrow`。`labor_daily_variable_share` 留空就沿用 `labor_flex.csv`；填了数字就覆盖。

按天模型和月度模型回答的不是同一个问题。月度选的是全年每个车间的 JPH 和班次；按天选的是这一个月里哪几天开焊装、哪几天开涂装。两边的「节约」不要加总。

### 2.5 可选扩展（文件不在 `data/` 里就没启用）

全成本示例包由 `python3 make_full_cost_plant.py` 生成到 `plants/FULL_COST/`。本厂要启用某一项，就把对应文件放进本厂配置包。字段以 `plant_check.py` 里的 `OPTIONAL` 为准。

| 启用什么 | 文件 | 使用时要注意 |
| :-- | :-- | :-- |
| 物料口径 | `mat_cost.csv` | 只进报表，不进求解目标 |
| 零件原币价 | `part_price.csv` | 价格 × `fx_rate`，优先于 `mat_cost.csv` |
| 边际贡献 | `margin.csv` | 目标变成「成本 − 边际贡献 × 交付」 |
| 间接定员 | `indirect.csv` | 按 JPH 档，并入人工 |
| 一次合格率 | `quality.csv` | 未建返修区时，有效产能再乘 FTT |
| 返修区 | `rework.csv` | 有返修区时 FTT 不再乘在产能上；有 `line_supply.csv` 时报废金额不按台再计一次 |
| 爬坡 | `ramp.csv` | 车间 × 月的系数 |
| OEE / 出勤 / 开动率 | `oee.csv`、`attendance.csv`、`avail.csv` | 有效产出 = 开动率 × OEE × 出勤 × 爬坡（及上面的 FTT 规则） |
| 换型 | `changeover.csv` | `mode=fixed` 或 `mode=color`。`mode=decision` 的代码还在，知识库确认之前不要用 |
| 涂装颜色 | `models.csv`、`color_batch.csv` | 配合 `mode=color` |
| 滑橇吊具 | `carrier.csv` | 有效缓存 = min(库容, 载体数) |
| 发运上限 | `shipping_cap.csv` | 启用后出现成品库和发货量 |
| 物流趟次 | `logistics.csv` | 入厂牛奶车若有 `fixed_month_cost`，低产量月份会改走远程卡车 |
| 叫料与线前库存 | `line_supply.csv` | 安全缓冲、在途、报废净率。缓冲公式本身仍待知识库确认 |
| 三厂订单上限 | `capacity_component.csv` | 同一车型同一月取各厂 `max_orders` 的最小。产量和发货都不超过它 |
| 折旧 | `asset.csv` | 启用后要把已含在 `oh_fixed_month` 里的折旧减掉，否则重复 |
| 模具摊销 | `tooling.csv` | 月固定，影响单车 |
| 周计划回写 | `slot_cap.csv` | 默认不自动改月模型。见第 5 节 `--apply` |
| 实际产量 | `actual.csv` | 只用于 `run_plant.py` 回测，不进优化 |
| 技能 | `skill.csv` | 只在周计划事后检查，不进月度求解 |

保修、碳：在 `global_params.csv` 增加 `warranty_per_unit`、`carbon_cost_per_unit`（以及碳配额相关键，缺省为 0）。

## 3. 策略：工厂想换一种排法

策略和基数是两层。基数是「工厂现在是什么样」。策略是「在这些数上，还额外要求什么」。

### 3.1 三种现成策略（演示和 `策略对比.png` 用的就是这三种）

定义在 `v5.2/strategies.py` 的 `STRAT`：

| 名称 | 额外约束 | 示例里适合用来说明什么 |
| :-- | :-- | :-- |
| 成本优先 | 无 | 最便宜的对照。人数可以逐月大起大落，招聘和培训没有单独计成本 |
| 稳定优先 | 相邻月 JPH 最多变一档；班次一季只在季初改一次；正常班利用率 ≤ 90%；加班上限 24 小时 | 用钱换「少跳档、少加班」，可能出现延期 |
| 保人力(人数月变化≤5%) | 各车间人数月环比不超过 5% | 人头稳住，波动靠加班顶 |

要改这三种的定义（例如把 5% 改成 8%，或把利用率改成 85%），改 `STRAT` 里对应的字典，然后：

```bash
python3 strategies.py
python3 diagrams/plot_strategy.py
```

结果在 `output/strategy_summary.csv`。这三种约束里，`head_change`、`jph_step`、`shift_quarter`、`util_cap` 还不能写进场景库 JSON，只能写在 `strategies.py` 或调用 `model_builder.build(...)` 的地方。

### 3.2 用场景库表达「如果发生某件事」

`data/scenario_library.csv` 加一行。`knobs` 是 JSON，在 CSV 里用双引号包住，内部双引号写成两次：

```text
8月冲量叠加限电,组合,8月需求+20%且开动率×0.85,"{""demand_month"": {""8"": 1.2}, ""avail"": {""ALL|8"": 0.85}}"
```

旋钮（全部是相对基准的覆盖，定义在 `scenarios.py` 文件头）：

| 旋钮 | 例子 | 作用 |
| :-- | :-- | :-- |
| `demand_all` / `demand_month` / `demand_model` / `demand_cell` | `0.9`、`{"10": 1.25}`、`{"10\|V451": 1.3}` | 需求系数，连乘 |
| `avail` | `{"BIW\|5": 0.8, "ALL\|7": 0.8}` | 开动率系数，`ALL` 表示所有车间 |
| `down` | `{"BIW\|6": 5}` | 停线天数 |
| `supply` | `{"V451\|4": 0.7}` | 零件供应上限 = 系数 × 当月该车型需求 |
| `elec` / `wage` / `gas` | `1.2` | 电价、工资、气价乘子 |
| `tou_version` / `voltage` | `"2024"`、`"10kV"` | 换电价版本或电压 |
| `weekend_policy` | `{"PNT": "hold"}` | 某车间周末保温或停炉 |
| `ot` | `24` | 所有车间加班上限（小时/月），常规和绝对上限都设成这个数 |
| `penalty` / `penalty_mul` | `200000`、`2` | 流失惩罚的绝对值，或再乘一次 |
| `backlog_mul` / `night_mul` | `2` | 延期成本、夜班补贴的乘子 |
| `max_shifts` | `2` | 去掉更高班次，保留 0 班 |
| `dispatch` / `stop_pay` / `borrow` | `0.2`、`0.7`、`0` | 覆盖全部车间的派遣比、正式工停工发薪、借调上限 |
| `switch_cost` / `switch_days` | `300000`、`2` | 换档一次的费用和损失天数 |
| `no_flex` / `no_switch` | `true` | 关掉停工日与借调，或关掉换档 |
| `buffer` | `{"ALL": 0.5, "PNT": 0.3}` | 缓存上限乘子，车间键优先 |
| `ftt` / `oee` / `attendance` / `ramp` | `{"PNT": 0.93}`、`{"PNT\|10": 0.9}` | 写成绝对值（OEE 在已有历史表上是再乘一次） |
| `cap_mul` | `1.15` | 车型月上限乘子 |
| `fg_hold` | `800` | 成品持有（元/台·月）。大于 0 就启用成品库，总装可以提前做 |

跑一条：


### 3.3 工厂用来拍板的一批问题

`lab/factory_analysis.py` 在基准上扫需求、车型、供应、停线、开动率、价格和管理约束，写出 `output/analysis/cases.csv`、`findings.csv`、`决策说明.md`。

默认只算常规范围。订单从一半扫到两倍、办法组合和假设冲击，把 `data/switches.csv` 的 `extreme` 改成 `1`，或运行时加上 `--extreme`。临时关掉用 `--no-extreme`。这一开关不改变基数。

```bash
python3 lab/factory_analysis.py
python3 lab/factory_analysis.py --extreme
```

管理约束（禁三班、加班 24 小时、人数月变化 ≤ 5%、几乎不能加人、节拍每月一档且班次按季锁定、利用率 ≤ 85%、禁止借调）写在这个脚本的情景目录里。工厂要增删问题，改 `catalog()`，不要改求解公式。

### 3.4 加权目标扫描（慢，和上面三种策略不是同一套数）

`lab/strategy_v5.py` 用权重扫「稳定 / 交付 / 人力」，再按阈值推荐。权重换算和阈值是代码里的 ⚠ 示例：人数变化 3000 元/人、积压 5000 元/台·月、人数 1000 元/人·月；波动 ≤ 30%、延期 ≤ 800 台·月、不允许流失、成本不超过成本优先的 5%。

改阈值改 `lab/strategy_v5.py` 的 `THRESH` 和 `GRID`。整条决策链（极限、扫描、推荐、风险、瀑布）是：

```bash
python3 lab/run_v5.py
```

这一条很慢，改一张工资表不必跑它。输出在 `output/v5/`，含 `管理层决策单.md`。扫描用的求解间隙比 `run.py` 宽，两套结果的总成本可以差一万元左右，在容差里，不要当成两次业务口径。

### 3.5 按天的开停策略

`daily.py` 比较连续三班、同步开停、模型自己选的开停。参数在 `daily_config.json`。和月度策略分开读：按天回答「这个月哪几天开线」；月度回答「这一年每个月用哪一档、开几班」。

## 4. 计算：公式在代码里，改完要留证据

工厂确认「算法和财务口径不一致」时才改代码。只改一个函数，并加一条用手算对得上的测试。

| 要改的计算 | 函数 |
| :-- | :-- |
| 有效产出（开动率 × OEE × 出勤 × 爬坡，以及 FTT / 返修） | `cost_functions.output_factor` |
| 正常班产能、加班产量 | `cost_functions.capacity`、`ot_units` |
| 加班单价 = 月薪 / 标准月工时 × 倍数 | `cost_functions.ot_rate` |
| 人工、夜班、福利 | `cost_functions.labor_breakdown` |
| 停工日可省比例 | `labor_flex` 读入后的公式（φ 见 `发布/版本记录/v5.2升级说明.md`） |
| 分时电价、启停炉、气 | `energy.py` |
| 月度目标和约束（选哪一档、延期、流失、借调、换档） | `model_builder.build` |
| 按天开停 | `daily.build` |
| 报表科目怎么加总 | `report.py` |

改完：

```bash
python3 -m pytest tests/test_v52.py tests/test_v4_rules.py tests/test_units.py -q
python3 run.py
```

`run.py` 会和 `golden.csv` 比四列：总成本、产量、缺口、延期台月。容差是 0.05% 和 2 万元里的较大者（产量、缺口、延期的下限是 5）。差在容差内会打印通过；超出只打印差异，不中断写结果。

确认新结果就是想要的口径之后，才更新基线，并在 `CHANGELOG.md` 写日期、改了什么、为什么、结果差多少：

```bash
python3 golden.py --update
```

没有确认之前不要 `--update`。需求 −10% 这一场景在 120 秒时限下，曾经停在比 golden 高约 189 万元的另一可行解上，那是时限，不是公式被改过。

`run.py` 里写死的五个场景是：基准、需求 ±10%、电价 +20%、工资 +5%。这五个是回归用的，不是工厂场景库。工厂自己的问题放进 `scenario_library.csv` 或 `factory_analysis.py`。

## 6. 读结果时固定要核对的几点

- 页眉或 `plant.json` 的 `config_version` 还写着「示例」时，数字不能报成工厂实绩。
- 总成本里制造费用（OH）在产量不变时几乎不动。讲节约时看人工、加班、能源、停工日、换档，并写出和基准的差额。
- 单车成本随产量下降而上升，多半是固定费用摊到更少的车上。
- 月度借调净额先搁置，等按天模型确认同一天有空闲人力，再决定要不要计这笔。
- 派遣比 20% 在登记表里仍是 ⚠。HR 确认之前，不要用它论证「多停几天更省」。
- 电价上涨而总装班次不变，说明这套示例里调班躲不开电价；换成工厂自己的峰谷和班次时刻后要重算，不能沿用这句结论。
- 需求下降后天然气往往不会按产量同比例下降：节拍变低时，烘房按小时烧，单台用气可能更费。
- 求解时限到了仍可能显示 Optimal。和上次差一截时，先看 `solver_time_limit` 和 golden 打印，再查是不是有人改了公式。
